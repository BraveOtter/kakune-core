# Core distribution

Release archives contain the `kakune` executable, both project READMEs, the license, examples, and service templates. Verify `SHA256SUMS` before extracting an archive. GitHub release provenance can be verified with `gh attestation verify <asset> --repo BraveOtter/kakune-core`.

Extract the archive to a directory owned by the user or administrator and run `kakune init --data-dir <directory>`. The `packaging/linux/kakune-core.service` and `packaging/macos/dev.kakune.core.plist` files are templates: update their executable and data paths before installing a service.

## Daemon and system-service scope

`kakune daemon start|status|stop` controls a background Core owned by the current OS user. The distinct `kakune service install|start|status|stop|uninstall` commands target the machine-wide native manager: Windows SCM (`KakuneCore`, `LocalSystem`), Linux systemd (`kakune-core.service`, `root`), or the theoretical macOS launchd system job (`dev.kakune.core`, `root`). Machine-wide operations require administrator/root permissions. The packaged systemd unit and launchd plist are not user units or agents.

Use an explicit absolute `--data-dir` when installing, and ensure it is accessible to the installed service account. Provider credentials are identity-bound: Windows Credential Manager data for an interactive user is not inherited by `LocalSystem`, and user Secret Service/Keychain entries are not automatically available to a root service. Do not copy token values into unit files, logs, or command lines. An inaccessible account-bound credential must be reported as a readiness failure; it must not be replaced or silently bypassed. A desktop-less deployment must deliberately configure the encrypted vault and securely supply its unlock material through the service manager, as described in the root README.

Installation requests automatic boot registration but leaves the service stopped. Equivalent registration is a no-op; conflicting executable, arguments, data path, account, or boot policy are not silently rewritten. Start requires observed Core readiness. Stop requires confirmed Core exit and native stopped state; uninstall must not remove registration after an uncertain/failed stop. Uninstall removes only the owned native registration and preserves workflows, configuration, credentials, execution history, logs, and data. Resolve old or conflicting definitions with an explicit stop/uninstall/reinstall procedure; never delete persistent data or rotate credentials as an upgrade shortcut.

Service operations have bounded application-controlled waits: 10 seconds for acquisition, status, preflight/reconciliation, helper work, and stop dispatch; 30 seconds for readiness/Core grace, install, and removal. Aggregate wait ceilings are 50/50/60/90 seconds for install/start/stop/uninstall. They are not wall-clock guarantees for filesystem, credential-store, or platform calls without safe cancellation. A timed-out client may have already submitted an operation to SCM/systemd/launchd; inspect actual manager state and the journal before retrying. Journal roots are ProgramData `Kakune\lifecycle\services` on Windows, `/var/lib/kakune/lifecycle/services` on Linux, and `/Library/Application Support/Kakune/lifecycle/services` on macOS. Status is read-only and unknown/inaccessible state is not absence.

Recorded native Windows SCM/LocalSystem and Linux systemd/root acceptance is available in [T044](../specs/002-daemon-service-commands/t044-windows-service-acceptance.md) and [T045](../specs/002-daemon-service-commands/t045-linux-native-acceptance.md), including automatic boot and retained-data reinstall. Those reports apply to their recorded binaries/scenarios; the [Phase 7 hosting refactor](../specs/002-daemon-service-commands/phase-7-audit.md#final-closure--2026-10-22) passed the default Windows suites, not a new native service/boot run. Native acceptance tests require an explicitly approved disposable machine or VM. Linux compilation/native acceptance is not established by a Windows build; macOS remains theoretical. No command should be used to mutate an existing unrelated registration.

Windows installers and macOS notarization are published only after their respective signing credentials are configured. An unsigned archive is always labelled unsigned.
